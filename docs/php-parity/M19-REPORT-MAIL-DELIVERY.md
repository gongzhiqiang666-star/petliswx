# 报告邮件发送增量

## 源码契约及实现落点

只读依据：原 Base.php::sendmail、lb_dictmaildiagnosisreport，common.php::GenterPdf/filterContents，以及 project/LbDiagnosisdetail.php::edit。

新入口为PC送检管理的“检测明细 → 报告邮件”，Java为LegacyReportMailController/Service。报告与收样通知共用LegacyBusinessMailService的持久化领取、投递、核对、取消和回写恢复；保留原LegacySampleNoticeService入口、参数及旧请求指纹格式，避免重复实现投递协议。

| 原业务 | 新系统行为 |
|---|---|
| 编辑页读取已保存MailTitle、Info.MailReport | 默认读原值，可编辑本次发送内容；不自动改写已保存副本 |
| 显式载入邮件模板调用filterContents，detailId为当前明细、type=1 | 复用已有绑定/日期/诊断项替换及原报告链接追加规则，不要求开启明细编辑能力 |
| GenterPdf按父单及明细编号、报告标题计算路径；文件必须存在 | 原命名规则独立实现，在私有报告目录检查文件、类型、大小与SHA-256；入队及投递前检查，变更则阻止发送 |
| 原附件调用行已注释 | 报告邮件不附PDF；仍要求先有对应文件，不套用财务邮件附件规则 |
| 成功后直接SQL更新明细IsSendMail=1、SendMailDt为当天日期，父单SendReportDt为当天日期、SampleStatus=3 | 按亚洲上海日期零点直写同样字段，不调用明细模型保存回调，不清空正文、不重算金额或改PDFHttpUrl |
| app.email环境覆盖同时改变To及BCC | 保留报告专用覆盖规则，与收样及财务邮件区分 |

## 参数与差异

独立配置legacy-report-mail，enabled/writeEnabled/sendEnabled/reconcileEnabled均须显式布尔真，后端与PC各自校验；实际SMTP还要求私有传输模式开启。PC入口位于明细列表，需要明细读取能力；报告模板渲染与发送不依赖明细写入开关。真实外发、作业及自动迁移保持关闭。

原邮件标题和正文允许为空，新报告接口保留这个行为，不强行填入新标题；收样通知原有必填规则不变。命名保留ASCII空格、引号、&、#处理、大小写PDF后缀、字面1970日期阈值及字符串0的追加行为。常用命名向量按源码测试，未声称完成所有PHP历史命名差分。

安全边界：联系人限定当前医院；文件不得越过当前编号目录、不得包含路径分隔符或通过符号链接读取任意文件。新接口只读取既有PDF，不生成、不替换、不修改原PHP文件；非PDF明确拒绝。必需但不附加的PDF采用流式摘要，不套用SMTP附件20MB上限。虚拟路径/Content/FilePdf/编号/文件映射到app.pdf.storage-path/编号/文件，与既有鉴权PDF读取保持一致。若历史资料涉及安全边界，需逐项核实兼容，不静默删减业务。

## 验证

- 报告数据库业务6项、文件与命名规则2项、共用收样业务10项、传输7项、原明细15项及绑定4项，相关测试方法共44项通过，无跳过；PC139项通过。文件规则包含21MB合成文件的元数据检查，不把它当成复杂PDF排版验收。
- 报告专项覆盖读取已存正文、显式模板替换、空标题/正文、成功直写字段、重复调用不再发送、人工确认接受后只回写，以及PDF缺失/变更/越界/符号链接拒绝。
- 实际PC→Java→本机13306→自建SMTP通过：打开报告邮件、读取原正文、查看已准备的PDF、编辑中文正文并发送、重复调用只接受一封，收到的Message-ID与尝试记录一致，且无附件。
- 合成主单/明细及正文副本逐字段比较，仅原四个发送字段改变：明细IsSendMail/SendMailDt、主单SampleStatus/SendReportDt。金额、正文、PDFHttpUrl及其他字段保持。合成数据/审计/PDF清理，开关恢复，临时Java/SMTP停止。
- 共用引擎改动后，真实PC收样通知“拒收→核对→另行重试”回归通过，SMTP最终接受一次，主单只改变收样通知标志。

## 未完成及证据边界

本次PDF是单独准备的合成文件，发送入口没有实现报告物理生成，不代表排版、正文与PDF语义一致、复杂历史素材或正式发布通过。既有PDF表格分页适配仍待用户选择。真实供应商、历史PDF定位、客户报告链接访问、新旧系统并发发送及完整两轮模块复核仍未完成。财务邮件仍待接入。
