# M24 支付单准备：原规则落库与请求恢复

## PHP 源码规则 → Java 实现

只读参考 `application/index/controller/Project/Pay.php::index` 第20–121行。`LegacyBankPaymentPreparationService` 复用已核价的明细选择，保存原支付主单和支付明细：

- `HostId=0`，`AliTradeId=''`，`IsSuccess=0`；`CHKMoney` 是逐项两位向零截断的核价总额，不是充值金额。
- 单号模式保留 `订单:单号`、空 PayMonth、`单号_明细ID列表` 的 Md5Id；月份模式保留医院日期区间、月初时间和医院名称备注。Md5Id原本不是哈希。
- 明细 PayMoney、ShowMoney 使用原 TestPrice，UserNo 使用原送检单号。医院资金、个人钱包、临床明细付款状态、父单状态及正文均不在准备时更新。
- 银行单号保留商户编码、上海时区当前日期/时间、月账医院最少六位及100–999随机后缀。新增Java请求检查已有单号，碰撞有限次重选，不能覆盖原单。

## 新 Java 可靠性与开关

已接入PC核价后的“保存支付单”确认框，以及当前账号的请求记录分页查询和刷新恢复。新增 POST/GET `/admin/legacy/bank-payments/requests`、GET `/requests/{key}`；不提供银行发送或扣款按钮。`legacy-bank-payments.enabled`、`prepareEnabled` 均须严格布尔true，ADMIN权限和真实事务必须同时成立。默认未启用。商户编码仅由后端 `app.legacy-bank.merchant` 提供，前端不能传入或替换；未配置或非法时能力为false且创建接口拒绝。验收只传入合成商户 TESTLOCAL，没有使用真实银行凭据。

主单、分摊、`lin_order_idempotency` 的独立 `LEGACY_BANK_PREPARE` 请求及审计同事务保存。幂等唯一键复用原Java表，不执行DDL。相同操作者/请求键/参数/商户恢复原记录；更改金额或其他请求参数拒绝。READY不因过期时间到达而删除或自动重建。

操作参数行锁对新的Java准备请求串行化；临床父子行锁及视图当前读重新核价，避免用旧快照保存变化项目。原PHP不遵守新请求锁，**未证明新旧支付并发安全**，正式接入前必须验证路由与双写竞争，不能据此宣称已解决。用户ID行锁只针对当前操作者。

## 明确差异及未完成

- 原PHP查询没有ORDER BY，Java继承核价的明细ID排序；Md5Id是同一组ID的稳定排序表示，原身份字段内容顺序可能不同，未证明历史外部消费者是否依赖该顺序。不能宣称逐字节等价。
- 旧Md5Id字段100字限制和现有Java请求医院有符号整数容量仍限制大单及极端医院ID；本实现显式拒绝而不截断，不擅自改原表。超限处理需业务方案/必要DDL审批。
- 日期仍仅支持YYYY-MM；PHP宽松日期入参未全部迁移。
- 未接银行请求发送持久状态、供应商未知结果恢复、查询/回调结算、退款、客户授权或原链接接续。当前READY只证明已保存意图，不代表供应商受理或付款成功。上述缺口全部保留在M24，整模块两轮复核尚未完成。

前端请求键当前覆盖同一核价确认框的关闭重开与重试；整页刷新后通过当前账号记录找回已保存支付单。尚未实现“浏览器刷新时原请求仍在处理中”的持久待确认操作恢复，也未证明不同请求键对应同一临床明细的并发收款安全；银行接通前继续补齐，不把本次响应丢失测试扩大为所有支付异常已验收。
