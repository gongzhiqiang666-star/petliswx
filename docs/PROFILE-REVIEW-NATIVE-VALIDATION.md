# 医生资料重审与跨医院权限接续

## 修复范围（2026-11-08）

原生资料页加载失败的重试误绑提交；提交POST成功但随后历史读取失败时，成功状态没有写入，仍可重复提交。现已区分加载/搜索/上传/提交/历史失败，成功POST立即锁定成功状态，历史失败只刷新历史。已有待审申请进入页面直接显示待审；被驳回后恢复原申请的姓名、职称、头像、医院和文件供修正。忙碌时文件选择与字段修改有保护。

提交端在锁用户后用READ_COMMITTED重新检查待审申请，避免并发请求使用旧快照插入多条待审；重复返回业务409，不改既有单条申请语义。

原审核只更新lin_user.hospital_id，显式DOCTOR角色仍指向旧医院，导致新资料与数据权限不一致。现在通过审核时同事务同步普通医生角色的hospital_id/scope_id；目标医院有停用历史角色时复用目标并停用旧角色，不撞唯一索引。无显式角色的旧医生沿用登录医院回退规则。管理/多机构/异常角色归属账号阻止自动迁移，保留待审申请，要求先核对角色，不把医院管理权限自动搬到新医院。迁移留PROFILE_HOSPITAL_CHANGED前后审计；沿用既有credential_version撤销旧会话。

PC资料审核增加姓名、职称、医院及头像状态的前后对照、资质鉴权下载；不自动加载申请中的任意头像外链。列表不再显示整段JSON，审核操作捕获打开时的类型，异步切标签避免旧结果覆盖。

以上均为应用逻辑及已批准表中的正常业务写入，没有DDL或原PHP表结构修改。

## 实际验证

仅本机隔离库合成医生760/同院同事761、原医院3274/新医院3275，无真实短信、外部发送或生产操作。

1. 四并发资料申请仅1条成功、3条409，待审期间医院资料不生效；同事不能审核。申请15驳回，requestedData与意见留存。

3. ADMIN正常接口批准16，先前有效HTTP会话立即401/403；重新登录显示新医院、姓名、头像。新头像真实HTTP字节与本次PNG一致，审核员可下载两份真实PDF资质。
4. 审批前医生可读原医院同事上传的GENERAL文件，审批后同一文件业务403；原同事仍可读。新医生上传文件归属新医院，原同事不能读；旧医院活动角色为0，仅1条迁移审计。
5. 原生重新登录回看批准后的新医院、头像、姓名与approved记录通过；各阶段finally均正常恢复原模拟器账号并刷新私有会话，临时沙箱文件移除。
6. 追加同医院申请17验证PC真实前后对照、两份资质下载入口及医院名称；空驳回原因保持表单，填写原因后正常驳回。该追加申请不改变16已生效资料，未再次迁移医院。

业务拒绝可能通过HTTP200+JSON code403返回；验收检查业务码和文件内容，不仅检查传输状态。首次审批脚本在旧会话失效断言通过后因仅按HTTP状态检查文件拒绝而停止，已修正并接续，没有重复审批或重放迁移。
