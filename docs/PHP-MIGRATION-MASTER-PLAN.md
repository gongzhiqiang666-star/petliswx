- 全部实际业务仍按32组模块迁移，先完成业务等价和逐项验证，再统一完整送检到报告流程。原PHP及已写覆盖层不改，数据库/生产/外发审批约束继续有效。

## 已批准迁移原则：先一比一保真，再统一全流程（2026-11-08）

用户已明确同意PHP整体业务迁移方案。以下原则优先于下文历史“仅分析/待范围批准/自行取舍”的要求：

1. 第一阶段先照搬全部原有实际业务能力，力求功能、展示内容和业务逻辑一致；不是只迁页面或只迁主流程。普通迁移工作按已批准批次推进，不逐项重复申请范围确认；数据库结构、生产/外发等原审批边界仍有效。
2. 已有PHP生产业务与我们当前实现发生冲突或不一致，以PHP业务规则为默认基准，保留原字段、展示内容、算法精度/运算顺序、默认值、状态及副作用。不得为了套现有新服务或简化实现而删减、替换。新功能无原PHP对应时，以我们现有逻辑和流程为主；交叉点单列映射与差异。
3. 原模型保存前后回调、隐藏接口、父类/trait继承动作、JS触发、视图/SQL计算、批量/导入导出/打印/通知及作业中的实际业务全部纳入。无菜单、无显式控制器实现、难测或资料不全均不是删除理由。未确认项保留待核验，不能标完成。
4. 医院资金与医生个人钱包保留两个独立资金池并向有权限的用户提供入口：独立余额/流水/权限/用途/核销退款归属，清楚标明资金池。不得合并余额、跨池自动扣款或重复记账；未有原规则或明确需求，不新增自动划转。
5. 第一阶段界面风格统一为我们的设计，业务上不顺带重设计已有PHP业务、改报告内容/列项/计算/审批条件；功能保真验收后再统一串联优化。迁移发现缺陷或不确定规则，登记差异、证据和影响，不擅自按新逻辑修掉导致行为改变；安全访问方式不得等同于业务能力，必要受控实现要保留业务并说明差异。
6. 原PHP源码、本机PHP副本和已写覆盖层继续冻结，已有内容不删不回退。迁移实现写在我们的小程序、PC管理端和Java，最终不依赖PHP桥接完成业务。
7. 总出口是完整送检到报告链路与所有迁移业务能力不丢失。每项实际业务须有原来源、新入口/服务、展示与逻辑对照、状态/数据/副作用及正反例证据；任何未迁移、未验证、缺资料或未解释差异都不能算全量完成，也不能因切换使功能消失。PHP停用/正式切换另行决定。

实施主计划：docs/PHP-MIGRATION-MASTER-PLAN.md。当前写入的是批准原则和验收门槛，不是功能已实现或已验证的声明。



## 1. 本次范围与执行顺序

先暂存“现有新系统独立全流程验收”目标，完整梳理PHP业务，再将批准的业务功能和算法迁入小程序、PC管理端、Java后端，最后统一串联端到端流程。原PHP源码、已有本机PHP覆盖层均保持不动；不为迁移继续给PHP补页面或接口。本轮只读源码/本机数据库元数据及菜单，编写文档。

迁移后的业务、计算、文件、权限和状态由Java统一提供；PC承接运营/实验室/财务/基础资料管理，小程序承接医生与医院日常操作。第一阶段按我们的统一显示风格承接PHP原有功能，展示内容、计算方法和逻辑保真迁入，不借换肤或组件替换重设计原业务。新系统已有能力先差分：符合的复用、缺少的补齐、已有PHP业务冲突的以PHP为准；新增业务沿用我们的逻辑。主业务数据避免重复；医院资金与个人钱包是两个独立账户体系，不能为了“统一”合并。

**先统一数据和状态契约，再逐模块迁移；全局联调在模块就绪后完成。** 不能等所有页面写完才解决金额、编号、权限和状态冲突。每个模块仍先完成自身测试，最终再做同单完整流程。

## 4. 核心算法与必须解释的差异

### 4.1 金额不能“差不多一致”

1. **折扣计算**：原Base.php:price为先bcdiv(discount,10,2)，再bcmul(ratio,price,2)，是分步截断；ContractService当前为list×rate÷10后HALF_UP到两位。例：价格88.88、折扣8.88，按原源码公式为78.21，新公式为78.93（数学对照，不冒充已运行原PHP端点）。迁移必须为旧业务保留明确的旧算法策略及计价快照；新协议价保留其既有契约。不能统一换一个舍入方法后重算历史订单。
2. **医院余额**：原basedata/Infohospital_money模型在流水新增前拒绝0金额、检查负向余额不足，再bcadd两位更新医院amount。它和lin_user个人money不是同一个资金池。新服务须锁医院账户、写流水与改余额同事务、稳定请求号防重，验证两并发扣款不透支；不能把旧余额转成个人余额。
3. **明细核销**：PayStatus2的0/1/2/3/4分别未结/现金/转账/网银/忽略，IsCheckPass=1还存在“免除”含义。迁移保留明细值和聚合口径，不与新IsPayMoney或微信支付结果合并成一个布尔值。
4. **费用汇总**：getFee按有效明细DetailIsActive=1且IsCheckPass=0汇总TestPrice、未结/已结；财务页当前页合计与全量合计要分别核验。批处理又按UserNO汇总回写付款标志，混合状态时必须记录原输出和风险。
5. **月报**：收样日期ReceiveSampleDt与SendMailDt统计视图并存，不同口径不可混成一份新月结账单。月末、闰日、时间边界、已通知、免除/作废明细都需黄金样本。

### 4.2 报告、编号与隐式行为

- LbListdiagnosisproject beforeInsert会写55550-前缀和1900日期、清空若干字段，后台add先建空主单再编辑；不能拿这个流程直接覆盖小程序一次完整提交。保留旧数据/ID与合规默认行为，但不要把清空有效输入的缺陷机械复现。
- LbDiagnosisdetail beforeInsert有count+1参与GenterNO、项目1225备注必填；新编号并发策略须兼容旧号，不覆盖已有号。1225的业务含义/跨库ID映射要确认，不能随意删除硬编码规则。
- beforeUpdate可因SendMailDt存在而联动主单完成并生成PDF，afterWrite写明细正文副本。第一阶段保留原触发条件、时序与实际业务副作用；不得直接用我们已有审批状态机替换PHP原保存/生成/发送规则。若拆成显式命令，必须证明同等操作仍触发同等业务结果。生产规则与新审批约束冲突，先以PHP已有业务为基准登记映射；缺陷/访问安全差异单列，不擅自修改规则。
- filterContents绑定主单、医院、性别、物种、样本和明细视图，替换日期、报告/付款链接、标题/项目串，并排除项目246。字符串开头占位符的strpos行为、空值/HTML/Unicode/分页符、附件路径逐项比对。
- PDF文字/数值必须一致；字体、标题、签章/条码（以实际模板为准）、分页、表格和附件做视觉对照。旧文件不可因换模板被覆盖。临时下载成功不代表模板迁移完成。
- 客户数据组、管理员与会员、医院/实验室权限需完整映射；旧公开支付/查看链接不能作为新系统免鉴权的理由。

### 4.3 运行依赖与缺失资料

本轮直接执行本机php7.4的纯bcmath表达式返回“Call to undefined function bcmul()”。这只证明**当前本机PHP容器没有相应扩展**，不能据此判断线上也没有。未安装扩展、未改容器；原算法端点尚不能据此对跑。实施时先为差分工具准备经确认的可执行参考环境或取得历史输入输出，不拿Java自算结果冒充PHP黄金结果。

### 10.2 双资金池必须可用且清楚区分

医院资金池与个人钱包必须各自有适用角色可见的余额/流水和操作入口，遵循原业务权限及我们的新增业务规则，不把“保留两张表”当作已经供用户使用。

| 项目 | 医院资金池 | 医生个人钱包 |
|---|---|---|
| 归属 | 医院主体 | 个人账号 |
| 余额和流水 | 沿用原医院amount及对应资金台账语义 | 沿用个人money及个人资金台账语义 |
| 操作权限 | 依原医院资金业务映射授权，不向所有医生自动开放 | 本人使用；平台操作须相应授权 |
| 界面 | 标明“医院资金”，提供适用的余额/明细/业务操作 | 标明“个人钱包”，提供余额/明细及适用操作 |
| 收支/扣款 | 原PHP已有医院资金规则优先 | 新个人钱包业务按现有批准规则 |
| 退款/核销 | 关联原交易及原资金池 | 关联原交易及原资金池 |

用例必须证明：两个账户各自余额准确；同一金额不会被记入两池；权限不串；同请求只记一次；并发不透支；失败不出现只改余额或只写流水；退款回原池；用户能明确知道扣哪一个池。涉及可选择支付资金池的业务按原规则/已批准新增需求开放并清晰展示，不能暗中代选另一池。没有原业务依据或明确需求时不新增池间自动划转。

## 11. 重新整理后的落地方案：我们的界面＋PHP业务

### 11.1 迁移与不迁移的准确边界

| 层面 | 做法 | 验收要求 |
|---|---|---|
| 页面风格 | 使用我们的配色、图标、卡片、菜单、表单及移动端适配 | 同一套设计语言；不复刻PHP旧皮肤 |
| 页面内容 | 原业务字段、名称、单位、列项/合计、正文、状态说明完整迁入 | 内容逐项对照，无遗漏、改义、擅自合并 |
| 业务能力 | 原实际业务全部迁入，已有实现先复用校准 | 可操作、可查询、可追溯，隐藏入口/回调也有对应实现 |
| 计算和规则 | 原PHP业务按PHP规则；无对应的新功能按我们现有规则 | 相同输入得到等价金额、状态、文件、通知和资金副作用 |
| 技术组件 | 可替换编辑器、表格、上传和图标等技术外壳 | 原组件承载的实际能力和数据格式不丢失 |
| 不搬的部分 | 无业务依赖的旧皮肤、纯示例、PHP开发/安装/升级工具、临时调试外壳 | 记录排除理由和业务引用核验，不能按目录名排除业务 |

原先“照搬”指业务保真，不代表沿用旧界面。“保真后优化”指不先改生产业务规则，并不阻止从第一批就使用我们的视觉风格。用户同意的排除边界仅限技术外壳，原业务没有因此减少。

### 11.2 编辑器选型与集成边界

PC富文本编辑统一采用 **Tiptap开源核心＋按需开源扩展**，通过原生JavaScript接入当前管理端，不为一个编辑器重写整个前端框架。工具栏和对话框使用我们的样式；依赖经构建打包到本项目，不加载运行时第三方CDN，不把报告或模板传到编辑器云端。

选择依据：开源核心MIT、界面可自定义、支持扩展及HTML输出；官方资料：[概览与许可](https://tiptap.dev/docs/editor/getting-started/overview)、[HTML输出](https://tiptap.dev/docs/guides/output-json-html)、[表格扩展](https://tiptap.dev/docs/editor/extensions/nodes/table)、[图片扩展](https://tiptap.dev/docs/editor/extensions/nodes/image)。这些资料不证明任意旧HTML自动保真，也不把商业转换/分页功能算作免费自带能力。实施时锁定通过验证的具体包版本和许可清单，尚未安装依赖。

编辑器不是业务规则引擎：字段替换、特殊项目、计价、审批、报告版本和发送联动仍由Java按原PHP规则处理。PDF由我们的后端产生，不依赖编辑器商业云转换。

先建立旧编辑器实际使用能力清单：字体/字号/颜色、加粗/斜体/上下标、段落/对齐/缩进/行距、列表、表格与合并单元格/列宽、图片/尺寸/对齐、链接、复制粘贴、撤销重做、模板变量、HTML源码及分页标记等。每项按原模板和页面是否实际使用确认，不以该枚举限制范围；实际使用的必须支持。

兼容验证安排在B0末、B1之前完成，作为B4模板实现的技术前置：

1. 从原模板、报告及邮件取得脱敏代表样本，保存原HTML与预览/PDF基线；原生产内容不改写。
2. 验证导入、显示、不编辑保存、编辑后保存、重新加载及后端生成输出。未编辑的内容不因“打开页面”被重序列化覆盖。
3. 核对文字、表格/合并/列宽、图片/尺寸、链接、样式、变量和分页符。需要的属性用明确扩展/适配承接，不能因编辑器schema不识别而静默删除。
4. 上传继续走自有私有文件接口和权限，历史图片/附件链接不能丢；不自动抓取外部地址或上传到第三方服务。
5. 旧模板不支持时阻止覆盖并说明原因，保留原始内容；完成兼容前该项不能标通过、不能用纯文本替代富文本业务。若无法补齐，重新评估技术组件，保持业务范围不变。
6. 报告/PDF/邮件与原结果逐项、逐页比对。编辑器看起来正常不能替代打印/发送结果验收。

### 11.3 用户可理解的执行分组

32组业务模块归为7块，模块编号和范围不变：

1. 账号与权限：管理员/医生/会员、角色、客户数据组、机构范围。
2. 医院与基础资料：医院、联系人、地区/物种/品种/样本/验收字典。
3. 项目、价格与资金：项目、多价格、PHP折扣、医院资金与个人钱包两池。
4. 送检与样本管理：主单、明细、采样资料、审核、附件、筛选/导出。
5. 检测与报告：结果、原保存回调、模板变量、编辑器、PDF、审核/发送及通知。
6. 财务与支付：核销、医院月报、新合同账单、原支付/退款/回调、对账和旧链接。
7. 系统与隐藏业务：配置、审计、批量/导入/恢复、隐藏接口、作业业务与技术依赖。

执行仍按B0–B6依赖推进。原有业务展示和逻辑等价是每批出口，最终把这些模块与已有物流/顺丰/实验任务/复检接成完整送检到报告链路。两资金池对用户分别可见可用，不合并、不自动跨池扣款。
