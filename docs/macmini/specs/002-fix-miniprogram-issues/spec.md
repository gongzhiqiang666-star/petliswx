## 用户场景与测试 *(必需)*

### 用户故事 1 - 完成预约检测流程 (优先级: P1)

用户选择宠物后能够完成完整的预约检测流程,包括填写采样信息、其他信息、送检信息,选择检测项目,预览并提交预约申请。

**为什么是这个优先级**: 这是核心业务功能,用户无法完成预约会导致整个系统无法使用。

**独立测试**: 可以通过选择一只已存在的宠物,填写所有必要信息,选择检测项目并提交,验证整个流程是否可用。

**验收场景**:

1. **已知** 用户在宠物列表页面选择了宠物, **当** 点击"继续预约"按钮时, **那么** 系统跳转到预约信息填写页面
2. **已知** 用户在预约信息填写页面, **当** 填写采样信息、其他信息、送检信息时, **那么** 系统自动填充城市为当前医院所在城市
3. **已知** 用户填写完基本信息, **当** 点击"选择检测项目"时, **那么** 系统跳转到检测项目选择页面(支持过滤和筛选)
4. **已知** 用户在检测项目选择页面, **当** 选择一个或多个检测项目时, **那么** 系统显示已选项目数量和预估总价
5. **已知** 用户选择了检测项目, **当** 点击"下一步预览"时, **那么** 系统跳转到预约预览页面显示所有填写信息
6. **已知** 用户在预览页面, **当** 点击"提交预约"按钮时, **那么** 系统创建预约订单并显示成功提示
7. **已知** 用户选择了狂犬检测项目, **当** 芯片号和出生日期未填写时, **那么** 系统显示错误提示并阻止提交
8. **已知** 预约订单创建成功, **当** 跳转到订单列表时, **那么** 用户能看到新创建的订单显示在"草稿"状态

**验收场景**:

1. **已知** 用户打开宠物列表页面, **当** 页面加载完成时, **那么** 显示所有宠物的基本信息(中文名、品种、性别、年龄、主人)
2. **已知** 后端API返回标准WebAPI格式的字段, **当** 前端渲染数据时, **那么** 直接使用后端字段名显示所有信息
3. **已知** 宠物列表为空时, **当** 页面加载完成时, **那么** 显示空状态提示和"添加宠物"按钮

### 用户故事 3 - 修复订单列表显示问题 (优先级: P1)

用户在订单列表页面能正确查看所有订单信息,包括宠物名称、检测项目、订单状态和创建时间。

**为什么是这个优先级**: 订单管理是用户查看和管理预约的核心功能,显示错误会影响用户体验。

**独立测试**: 可以通过访问订单列表页面,验证所有字段是否正确显示。

**验收场景**:

1. **已知** 用户打开订单列表页面, **当** 页面加载完成时, **那么** 显示所有订单的基本信息(宠物名称、检测项目、状态、时间)

### 用户故事 4 - 显示真实用户和医院信息 (优先级: P2)

用户在"我的"页面能看到真实的用户信息和所属医院信息,而不是硬编码的假数据。

**为什么是这个优先级**: 虽然不影响核心功能,但影响用户对系统的信任度和专业性。

**独立测试**: 可以通过访问"我的"页面,验证用户信息和医院信息是否从API加载。

**验收场景**:

1. **已知** 用户登录并打开"我的"页面, **当** 页面加载完成时, **那么** 显示真实的用户姓名、手机号、邮箱等个人信息
2. **已知** 用户所属医院信息存在, **当** 页面加载完成时, **那么** 显示医院名称、地址、电话、营业时间等信息
3. **已知** API未返回用户头像, **当** 显示用户头像区域时, **那么** 使用默认头像占位符
4. **已知** 用户信息加载失败, **当** 发生网络错误时, **那么** 显示错误提示并使用缓存数据(如果有)

### 用户故事 5 - 简化"我的"页面菜单 (优先级: P2)

用户在"我的"页面只看到用户信息和医院信息卡片,移除所有菜单项(包括消息通知、系统设置、图标下载、帮助中心、隐私等),只保留退出登录按钮。

**为什么是这个优先级**: 简化UI可以减少用户困惑,让页面更专注于显示核心信息。

**独立测试**: 可以通过访问"我的"页面,验证只显示信息卡片和退出登录按钮。

**验收场景**:

1. **已知** 用户打开"我的"页面, **当** 页面加载完成时, **那么** 只显示用户信息卡片、医院信息卡片和退出登录按钮
2. **已知** 用户查看页面, **当** 浏览整个页面时, **那么** 不包含任何菜单项(消息通知、系统设置、图标下载、帮助中心、隐私政策等)
3. **已知** 用户信息和医院信息, **当** 显示时, **那么** 使用后端API返回的实际字段名和值

### 边界情况

- 当宠物列表为空时,预约流程应该引导用户先添加宠物
- 当API返回的数据字段为null或undefined时,前端应该显示默认值或留空而不是显示"null"或"undefined"
- 当网络请求失败时,系统立即显示友好的错误提示并提供手动重试按钮,不自动重试
- 当用户信息包含特殊字符或表情符号时,应该正确渲染而不破坏布局
- 当订单列表数据量很大时(超过100条),应该使用分页或虚拟滚动优化性能

## 需求 *(必需)*

### 功能需求

#### 预约检测流程相关
- **FR-001**: 系统必须在用户选择宠物后提供"继续预约"按钮,点击后跳转到预约信息填写页面
- **FR-002**: 系统必须在预约信息填写页面显示采样信息、其他信息、送检信息表单,并自动填充城市为当前医院所在城市
- **FR-003**: 系统必须在检测项目选择页面提供分类标签页(如血液检测、DNA检测、疫苗检测等),用户点击分类切换显示对应项目,支持搜索项目名称
- **FR-004**: 系统必须支持用户选择多个检测项目,并实时显示已选项目数量和预估总价
- **FR-005**: 系统必须在检测项目选择后提供预览页面,显示所有填写的信息和检测项目列表
- **FR-006**: 系统必须在提交预约前验证必填字段(宠物信息、采样信息、主人信息)
- **FR-007**: 系统必须在检测项包含狂犬检测(InfoTestTypeId=1225)时验证芯片号和出生日期必填
- **FR-008**: 系统必须在预约创建成功后显示成功提示并跳转到订单列表页面
- **FR-009**: 系统必须在预约流程中支持返回上一步修改已填信息

#### 宠物管理相关
- **FR-010**: 系统必须直接使用后端API返回的字段名(后端提供标准WebAPI接口)
- **FR-011**: 系统必须在宠物列表页面显示宠物中文名、英文名、品种、性别、年龄、主人姓名
- **FR-012**: 系统必须在空状态时显示友好的提示和添加按钮
- **FR-013**: 系统必须在编辑页面正确预填充现有宠物信息
- **FR-014**: 系统必须支持按宠物中文名、英文名、芯片号进行搜索

#### 订单管理相关
- **FR-015**: 系统必须使用后端API返回的字段名AnimalName显示宠物名称
- **FR-016**: 系统必须将SampleStatus状态码(-2,-1,0,1,2,3,4)转换为可读文本标签
- **FR-017**: 系统必须在订单列表显示宠物名称、检测项目、状态、创建时间等关键信息
- **FR-018**: 系统必须支持按状态筛选订单(全部、草稿、待审核、等待报告、已完成)
- **FR-019**: 系统必须在订单详情页面显示完整的检测项目列表和价格明细

#### 用户和医院信息相关
- **FR-020**: 系统必须在"我的"页面调用API获取真实用户信息(非硬编码数据)
- **FR-021**: 系统必须按后端API返回的实际字段显示用户信息
- **FR-022**: 系统必须调用API获取并按后端返回字段显示所属医院信息
- **FR-023**: 系统必须在用户头像未上传时显示默认头像占位符
- **FR-024**: 系统必须在API加载失败时立即显示友好错误提示并提供手动重试按钮,不执行自动重试

#### "我的"页面菜单优化相关
- **FR-025**: 系统必须从"我的"页面移除所有菜单项(包括消息通知、系统设置、图标下载、帮助中心、隐私政策等)
- **FR-026**: 系统必须在"我的"页面只显示用户信息卡片、医院信息卡片和退出登录按钮

### 关键实体 *(如果功能涉及数据)*

- **宠物(Pet)**: 包含中文名(animalName)、英文名(animalNameEn)、品种、性别(dictSexId)、年龄、芯片号(chipNo)、主人姓名(masterName)、所属医院、创建时间等属性
- **订单(Order)**: 包含订单ID、用户编号(UserNO)、宠物信息(关联Pet)、检测项目列表(多个DiagnosisDetail)、订单状态(SampleStatus)、采样信息、主人信息、费用、创建时间等属性
- **检测项目(DiagnosisDetail)**: 包含检测项ID、检测项名称、价格、生成编号(GenterNO)、支付状态、报告URL等属性
- **用户(User)**: 包含用户ID、微信openid、昵称、手机号、邮箱、所属医院ID、头像URL等属性
- **医院(Hospital)**: 包含医院ID、医院中文名、医院英文名、地址、电话、营业时间等属性

## 依赖和假设

### 依赖项
- 后端API已经按照PROJECT_COMPLETION_REPORT.md中的定义实现并可用
- API接口返回的数据格式符合api/index.js中定义的接口
- 用户已经完成微信登录并持有有效的JWT token

### 假设
- 后端API提供标准WebAPI接口,字段命名遵循后端规范
- 前端直接使用后端返回的字段名,不做转换映射
- 所有API错误都应该在前端统一处理和显示用户友好的错误信息
- 用户使用的是较新版本的微信客户端,支持小程序的所有必要API
