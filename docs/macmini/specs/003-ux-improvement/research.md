**Feature**: 003-ux-improvement
**Date**: 2025-12-28
**Phase**: Phase 0 - Research & Decision Making

## 概述

本文档记录了 PETLIS UX 优化项目的所有技术决策和调研结果。通过研究现有代码库、数据库结构和 API 接口,我们解决了所有在 Technical Context 中标记为 "NEEDS CLARIFICATION" 的技术问题。

## 研究问题 1: 现有后端 API 是否完全满足新功能需求?

### 问题背景
新功能需要搜索、分页、排序等功能,需要确认现有 API 是否支持。

### 调研发现

通过检查 `miniprogram/api/index.js`,我们发现:

#### ✅ 已支持的 API 功能:

1. **宠物搜索**:
   - `pets.search(name)` - 按宠物名称搜索
   - `pets.getList(params)` - 获取宠物列表,支持分页参数 `{pageNum, pageSize}`
   - **结论**: 基本搜索功能存在,但缺少按主人姓名搜索

2. **报告查询**:
   - `reports.getList(params)` - 获取报告列表,支持多参数筛选 `{pageNum, pageSize, petId, status, startDate, endDate}`
   - **结论**: 支持基本筛选,但**缺少排序参数**(申请时间、发布时间排序)

3. **数据字典**:
   - `dictionary.getSexes()` - 获取性别列表
   - `dictionary.getAnimals()` - 获取动物物种列表
   - `dictionary.getVarieties(animalId)` - 获取品种列表,支持按物种筛选
   - **结论**: API 存在且设计合理

#### ❌ 缺失的 API 功能:

1. **宠物搜索增强**:
   - 缺少按主人姓名搜索的功能
   - **建议**: 在后端新增 `GET /pets/search` 接口,支持参数 `{name, masterName, pageNum, pageSize}`

2. **报告排序**:
   - `reports.getList()` 缺少排序参数(sortBy, sortOrder)
   - **建议**: 新增排序参数 `{sortBy: 'applyTime'|'publishTime', sortOrder: 'asc'|'desc'}`

3. **宠物详情返回畜主信息**:
   - 需要确认 `pets.getDetail(id)` 是否返回畜主信息
   - **建议**: 确保 API 返回包含畜主姓名、电话的完整信息

### 决策

**Decision**: 现有 API 基本满足需求,但需要**小幅增强后端 API**

**具体行动**:
1. 后端需要新增/修改以下接口:
   - `GET /api/pets/search` - 增强搜索功能,支持主人姓名和分页
   - `GET /api/reports` - 新增排序参数(sortBy, sortOrder)
   - `GET /api/pets/:id` - 确保返回畜主完整信息

2. 前端适配:
   - 如果后端 API 无法及时修改,前端可以先使用**本地搜索**(获取所有数据后前端过滤)作为临时方案
   - 但这不符合性能要求(数据量大时性能差),仅作为降级方案

## 研究问题 2: 性别字典 API 当前是否存在且返回完整选项?

### 问题背景
当前性别选择只显示"-"和"已绝育",但实际应该有4个选项(未知/公/母/其他)。

### 调研发现

通过查询数据库 `lin_lb_dictsex` 表:

```sql
SELECT DictSexId, SexName, SexName_en, IsActive FROM lin_lb_dictsex
```

**结果**:
- 总共8条记录,但**只有1条启用**(IsActive=1)
- 启用的记录: DictSexId=8, SexName="已绝育", SexName_en="Neutered"
- 禁用的记录包括: "雄性"(1)、"雌性"(2)、"中性"(3)、"绝育雌性"(4)、"去势雄性"(5)、"不详"(6)、"-"(7)

### 根本原因

数据库中的性别字典大部分被**禁用**(IsActive=0),导致 API `GET /api/dictionary/sexes` 只返回1条记录。

### 决策

**Decision**: 这是**数据问题,不是 API 问题**

**具体行动**:
1. **后端操作**: 需要更新数据库,启用必要的性别选项:
   ```sql
   UPDATE lin_lb_dictsex SET IsActive = 1 WHERE DictSexId IN (1, 2, 6, 8);
   -- 启用: 雄性(1), 雌性(2), 不详(6), 已绝育(8)
   ```

2. **前端适配**:
   - API `dictionary.getSexes()` 调用正常,无需修改前端代码
   - 一旦数据库更新后,前端会自动显示完整的性别选项

3. **建议的性别选项**(基于业务需求):
   - DictSexId=6: "不详" (Unknown) - 默认选项
   - DictSexId=1: "雄性" (Male)
   - DictSexId=2: "雌性" (Female)
   - DictSexId=8: "已绝育" (Neutered)

## 研究问题 3: 年龄计算应该在前端还是后端实现?

### 问题背景
需要显示宠物的年龄,可以基于生日计算,但不确定计算逻辑应该在哪里。

### 分析

#### 方案A: 前端计算
**优点**:
- 实时计算,始终基于当前日期显示准确年龄
- 减少后端 API 请求
- 前端可以根据不同场景灵活调整显示格式

**缺点**:
- 多个页面需要重复实现计算逻辑
- 如果后端需要根据年龄筛选,前端计算无法使用

#### 方案B: 后端计算
**优点**:
- 计算逻辑集中,易于维护
- 可以用于后端筛选和排序

**缺点**:
- 需要每次请求 API,无法实时更新
- 显示的是"存储时的年龄",不是"当前年龄"

### 决策

**Decision**: **前端实时计算**(基于当前日期)

**理由**:
1. 用户看到的是"宠物当前的年龄",而不是"建档时的年龄"
2. 规格说明明确要求:"使用当前日期作为计算基准"(实时显示宠物当前年龄)
3. 减少不必要的 API 请求,提升性能

**具体行动**:
1. **新增工具函数**: `utils/age-calculator.js`
   ```javascript
   /**
    * 计算宠物年龄
    * @param {String|Date} birthday - 宠物生日
    * @returns {String} 年龄字符串 "X岁Y个月" 或 "X个月"
    */
   function calculateAge(birthday) {
     // 实现逻辑
   }
   ```

2. **使用场景**:
   - 宠物列表页: 显示卡片上的年龄
   - 宠物选择页: 显示选中宠物的年龄
   - 报告详情页: 显示宠物年龄

3. **显示格式**:
   - 小于1岁: "X个月" (如 "6个月")
   - 大于等于1岁: "X岁Y个月" (如 "2岁3个月")
   - 无生日信息: "未知"

## 研究问题 4: 当前小程序使用什么 UI 组件库?

### 问题背景
需要了解当前小程序的 UI 体系,以便决定是否引入新的组件库。

### 调研发现

通过检查 `miniprogram/app.json` 和代码结构:

1. **未使用第三方 UI 组件库**:
   - 没有引入 Vant Weapp、WEUI 等常见库
   - 使用的是**原生微信小程序组件**

2. **当前样式体系**:
   - 全局样式文件: `app.wxss`
   - 自定义样式目录: `styles/`
   - 使用原生 WXSS 编写样式

3. **组件结构**:
   - 目前**没有自定义组件**目录(`components/`)
   - 所有页面都是独立的,组件复用度低

### 决策

**Decision**: **继续使用原生组件,但新增可复用组件**

**理由**:
1. 避免引入第三方库增加包大小
2. 保持代码简洁,减少依赖
3. 原生组件性能更好,且功能足够

**具体行动**:
1. **新增可复用组件** (放在 `miniprogram/components/`):
   - `search-input/` - 搜索输入组件(带防抖功能)
   - `pagination/` - 分页组件
   - `pet-card/` - 宠物卡片组件(包含年龄显示)
   - `species-selector/` - 物种选择独立页面

2. **设计原则**:
   - 组件化: 提取公共UI为可复用组件
   - 原生优先: 使用微信原生组件(view, text, picker等)
   - 样式统一: 使用全局样式类,保持视觉一致性

## 研究问题 5: 是否需要引入单元测试框架?

### 问题背景
前端代码质量保证,需要考虑是否引入测试框架。

### 分析

#### 微信小程序测试现状:
- **官方支持**: 微信开发者工具内置测试功能
- **第三方框架**: Jest + miniprogram-simulate(社区方案)
- **测试复杂度**: 小程序涉及原生API,测试难度较大

#### 本项目特点:
- 主要是UI交互改进(搜索、分页、布局)
- 业务逻辑相对简单(年龄计算、数据展示)
- 团队规模小,可能没有专门的测试人员

### 决策

**Decision**: **暂不引入自动化测试框架,采用手动测试为主**

**理由**:
1. UX 优化主要是 UI/交互改进,自动化测试性价比低
2. 年龄计算等简单逻辑可以通过手动测试验证
3. 小程序测试框架配置成本高,维护成本也高

**具体行动**:
1. **手动测试检查清单**:
   - [ ] 搜索功能: 输入后能正确过滤结果
   - [ ] 分页功能: 切换页面正常,数据不重复
   - [ ] 年龄计算: 验证边界情况(无生日、今天生日、去年生日)
   - [ ] 表单布局: 检查所有必填项验证
   - [ ] 性别选择: 确认显示4个选项
   - [ ] 报告排序: 切换排序方式结果正确

2. **代码质量保证**:
   - 使用 ESLint 进行代码规范检查
   - 复杂逻辑添加注释和示例
   - Code Review 确保代码质量

3. **未来考虑**:
   - 如果项目规模扩大,可以考虑引入 Jest
   - 如果有复杂的业务逻辑(如数据同步、状态管理),应该增加单元测试

## 研究问题 6: 页面布局居中问题的技术方案?

### 问题背景
规格说明提到"多个子页面未居中,整体布局偏右",需要确定修复方案。

### 调研发现

检查了现有页面的样式文件,发现可能的原因:
1. 缺少统一的布局容器
2. 使用了 `text-align: left` 但没有居中容器
3. 页面宽度没有限制

### 决策

**Decision**: 使用统一的页面容器样式

**具体行动**:
1. **在 `app.wxss` 中添加全局布局样式**:
   ```css
   /* 统一的页面容器 */
   .page {
     display: flex;
     flex-direction: column;
     align-items: center;
     min-height: 100vh;
     background-color: #f9fafb;
   }

   /* 内容区域 */
   .page-content {
     width: 100%;
     max-width: 750px; /* 小程序标准宽度 */
     padding: 0 32rpx;
     box-sizing: border-box;
   }

   /* 页面标题 */
   .page-title {
     width: 100%;
     max-width: 750px;
     padding: 32rpx;
     box-sizing: border-box;
   }
   ```

2. **需要修复的页面**:
   - `pages/pets/pets`
   - `pages/pet-add/pet-add`
   - `pages/order-select-pet/order-select-pet`
   - `pages/report-list/report-list`
   - `pages/order-add-pet/order-add-pet`

3. **修复方法**:
   - 在每个页面的 WXML 最外层添加 `.page` 类
   - 内容区域使用 `.page-content` 包裹
   - 统一样式,避免每个页面重复定义

## 替代方案考虑

### API 增强 - 替代方案

**方案B**: 纯前端搜索和分页
- **做法**: 一次性获取所有数据,前端进行搜索、过滤、分页
- **优点**: 无需修改后端,前端独立完成
- **缺点**: 数据量大时性能差(>1000条宠物时卡顿)
- **为何拒绝**: 不符合性能要求(搜索响应时间 < 1秒),仅作为降级方案

### 年龄计算 - 替代方案

**方案B**: 后端计算并存储
- **做法**: 后端计算年龄,存储在数据库字段中
- **优点**: 计算一次,多次使用
- **缺点**: 年龄不实时,需要定期更新
- **为何拒绝**: 用户期望看到"当前年龄",不是"建档时年龄"

### UI 组件库 - 替代方案

**方案B**: 引入 Vant Weapp
- **优点**: 组件丰富,样式统一
- **缺点**: 增加包大小(~200KB),学习成本
- **为何拒绝**: 当前需求简单,原生组件足够,避免过度设计

## 技术风险与缓解措施

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 后端API无法及时修改 | 前端使用降级方案,性能下降 | 中 | 实现纯前端搜索作为临时方案,后续替换为API搜索 |
| 性别字典启用后影响现有数据 | 可能导致旧数据显示异常 | 低 | 先在测试环境验证,确认兼容性后再上线 |
| 年龄计算逻辑错误 | 显示不准确年龄,影响用户体验 | 低 | 编写多个测试用例,验证边界情况 |
| 页面布局修改影响其他页面 | 可能引入新的布局问题 | 中 | 逐页面修改并测试,保留原样式备份 |
| 性优化达不到目标 | 搜索响应时间>1秒 | 低 | 使用防抖、虚拟列表等技术优化 |
