## 为什么需要独立持久化

现有 lin_shipment 可以保存最终运单，但没有网络请求预占、payload hash、未知结果、外部订单号和回调去重数据。不能在外部下单成功后才落运单：超时/断电期间第二端重试会重复寄件。运营配置表不是业务请求日志，不借其保存寄件状态。使用已获用户批准并在本机执行的 005-sf-express-integration.sql 两张新增表；不改原表或既有表结构。

## 下单与故障恢复

1. 鉴权：订单属于当前医院，实验室一致且审核/结算符合寄件条件；优先检查已有运单，拒绝同一订单再次寄件。
2. 短事务插入 lin_sf_request，唯一 order_id+operation 预占，保存稳定外部订单号和 payload hash。相同请求读取原结果；不同参数返回冲突，不能覆盖首次内容。
3. 提交预占事务后再调用顺丰。网络请求期间不持有数据库长事务锁。
4. 成功结果写入请求记录，并以相同订单唯一约束关联 lin_shipment；若本地写入失败保留外部订单号供对账，不重新寄件。
5. 请求超时/中断标记 UNKNOWN；进程崩溃遗留 SENDING 同样只能查单。查单确认无单且满足人工恢复策略后，才允许受控处理，不能只凭超时重发。
6. 取消也保存独立操作及结果，确认承运方取消后再呈现；已揽收不支持的情况明确拒绝。

## 路由与双端

验证回调认证后按稳定事件键去重，不按收到时间覆盖新状态；记录原码和业务发生时间。仅允许前进或显式异常/恢复状态。妥投到 DELIVERED，实验室真实核样操作才可进入 RECEIVED。新增表挂同一业务订单/运单 ID，PHP、PC 与小程序读取同一结果；旧 PHP 不能只读取原订单状态推断物流。

所有任务目前手动触发；不启用定时重试或自动外发。不保存生产凭据、完整请求地址/联系人到日志。面单文件接入 lin_file 鉴权下载。回调公网入口未经授权不暴露本机。官方沙箱查询与取消已通过协议验证。尚待面单、回调契约及测试、请求结果和运单关联、查单恢复及三端业务入口。
